1. Сервис парсинга ISO 20022 / SWIFT-подобных сообщений

Назначение
Приём, валидация и преобразование внешних финансовых сообщений во внутренний канонический формат для дальнейшей обработки в АБС/платёжном ядре.

Функциональные требования

    Приём сообщений из MQ, файлового хранилища, API или шлюза.

    Поддержка форматов: ISO 20022 (pacs.008, pacs.009, pain.001, camt.053), SWIFT MT103/MT202, XML/CSV-выгрузки.

    Определение типа сообщения и выбор схемы валидации.

    XSD/схемная валидация, проверка обязательных полей, валют, BIC/IBAN, контрольных сумм.

    Маппинг во внутреннюю модель: платёж, поручение, выписка, статус.

    Идемпотентность по EndToEndId / UTI / MsgId.

    Обработка ошибок: retry, DLQ, алерты, ручной разбор.

    Аудит: кто, когда, что принял и преобразовал.

    Метрики: количество сообщений, ошибок, задержки.

Стек

    Python 3.11+, FastAPI, lxml, xmlschema, Pydantic.

    PostgreSQL, SQLAlchemy, Alembic.

    RabbitMQ / Kafka, Redis.

    Docker, Kubernetes, Prometheus/Grafana, ELK/OpenSearch.

    pytest, CI/CD.

Интеграции
АБС, платёжный шлюз, SWIFT/СПФС, внутренние очереди, DWH.

НФТ и безопасность

    Задержка обработки — до 200 мс на сообщение.

    Горизонтальное масштабирование, отказоустойчивость.

    Шифрование каналов, ГОСТ TLS, разграничение доступа.

    Соответствие 152-ФЗ, PCI DSS, требованиям Банка России.

    Хранение аудита — не менее 5 лет.

Критерии приёмки

    Корректный разбор всех заявленных типов сообщений.

    Ошибки валидации не приводят к падению сервиса.

    Повторная доставка не создаёт дубль.

    Есть метрики, логи и алерты.

Сервис обработки PDF-документов (Celery-based)
Подтверждение архитектуры

Да, обработка PDF выполнялась асинхронно через Celery. Схема была такая:

    Producer — FastAPI-эндпоинт принимал файл, сохранял в S3/MinIO, создавал запись в БД со статусом PENDING и ставил задачу в очередь.

    Broker — Redis (или RabbitMQ) как транспорт задач.

    Workers — отдельные Celery-воркеры по типам документов (тяжёлые — на отдельных очередях, чтобы не блокировать лёгкие).

    Result backend — Redis/PostgreSQL для хранения статусов и результатов.

    Celery Beat — периодические задачи: ретраи, очистка временных файлов, переобработка упавших.

    Мониторинг — Flower для воркеров, Prometheus/Grafana для метрик, Sentry для ошибок.

Задачи в Celery были идемпотентными (по document_id + checksum), с acks_late=True, max_retries, экспоненциальным backoff и DLQ для «безнадёжных» задач.

Конфигурация воркеров (пример)

    Очередь light (текстовые PDF, реквизиты) — 8–16 воркеров, concurrency=4.

    Очередь ocr (сканы, паспорта) — 16–32 воркера, concurrency=2, GPU-опционально.

    Очередь heavy (договоры, NLP) — 4–8 воркеров, concurrency=1.

    Очередь retry / DLQ — отдельные воркеры с пониженным приоритетом.
